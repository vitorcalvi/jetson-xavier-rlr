# Xavier NX 8GB: exhaustive practical use-case catalog

**Scope.** This catalog describes the specific Xavier NX 8GB, DFRobot DFR1242 carrier, JetPack 5.1.7 / L4T R35.6.5, 10W profile, CUDA 11.4, TensorRT 8.5, 14GB eMMC plus slow SD, and failed fan documented in `RESULTS.md`. Research is off-device; no Jetson connection was made. Feasibility grades are for this unit as currently configured, with fan repair treated as a deployment prerequisite for sustained use. The catalog builds on `USE_CASES.md` with distinct workloads and domain coverage.

**How to read the grades.** *Great* = strong fit within a 10W edge role; *OK* = practical with workload shaping and integration; *Marginal* = narrow/small-scale demonstration or low duty cycle; *Poor* = resource, software lifecycle, accuracy-validation, or economics make it a bad choice as specified. Grades are engineering estimates, not guarantees. Measurements cited as `R` refer to the local `bench/RESULTS.md`; estimates extrapolate from those results and must be validated with actual cameras, models, streams, and carrier I/O. The DLAs are not additive to GPU figures: DLA and GPU can overlap, but graph coverage/fallback and shared memory matter. The baseline's YOLOv8n DLA run fell from 43.4 q/s standalone in one test to 35.6 q/s in the power test, and the dual DLA run lost throughput under simultaneous workloads.

## 3. Known limits and planning values

| Limit | Ground truth / implication |
|---|---|
| Shared memory | 8GB physical unified LPDDR4x; test log reports 6,833 MiB visible. End-of-run available RAM was 5.0 GiB; mixed Qwen+ResNet+Whisper used 4,421 MiB peak, and the later Qwen+YOLO+Whisper mix peaked at 4,494 MiB (R). CPU, GPU, DLA, video and OS share it; model memory is not dedicated VRAM. |
| LLM ceiling | Qwen2.5-0.5B Q4: 41.99 tok/s generation, 2,417 MiB peak; 1.5B: 15.98 tok/s, 3,029 MiB; Llama 3.2 3B: 9.47 tok/s, 3,958 MiB and needed `-b512 -ub128` after an allocation failure (R). Longer context and parallel users reduce headroom. |
| JetPack ceiling | Xavier NX runs JetPack 5.x / L4T R35 family, Ubuntu 20.04, CUDA 11.4, TensorRT 8.5.2; JetPack 6.x current stack is for Orin, not Xavier. NVIDIA's JP 5.1.7 page describes R35.6.5/Ubuntu 20.04/TRT 8.5.2 [S1]. |
| New AI precision/features | Volta compute capability 7.2 supports FP16/INT8 paths but lacks the later-architecture hardware paths for FP8; TensorRT documents FP8 features for Ampere-and-later compatibility paths, while NVIDIA release notes tie Transformer Engine FP8 model workflows to Hopper-class hardware [S15]. There is no measured TensorRT-LLM/Transformer Engine path on this generation. FP16 is demonstrated; calibrated INT8 is demonstrated for ResNet50 only. The R baseline's YOLO INT8 attempt produced no valid engine. |
| DLA limits | Two NVDLA engines exist, but not every graph layer is DLA-compatible. In R, YOLO DLA had GPU fallback (50 layers switched in one run; later audit showed 22 GPU / 1 DLA groups); dual DLA tests showed contention and did not scale linearly. Plan by measured end-to-end graph, not theoretical TOPS. |
| PVA / VIC | PVA + VPI and VIC can free GPU for suitable classical vision transforms; backend coverage is per-algorithm, and PVA is not necessarily faster than CPU/CUDA. NVIDIA VPI documentation describes this caveat [S4]. |
| Thermal / power | 10W profile; fan PWM 255 but tach 0 RPM. Combined workload peaked at 64.5°C in earlier run and 72.5°C in 60s mixed test; a later single Qwen evaluation reached the 78°C pause guard (R). Fix fan before long-duration/unattended workloads. VDD_IN samples: Qwen 1.5B 8.241W, ResNet FP16 9.575W, YOLO DLA 6.199W. These are measured input-rail samples, not whole-system guarantees. |
| Storage | 14GB eMMC root and slow SD are poor for model churn, DBs, NVR writes, containers, or large logs. Prior `USE_CASES.md` reports ~7 MB/s SD write; `RESULTS.md` reports only 2.0 GiB free on `/` and 106 GiB in `/models` at its recorded end state. Put weights, Docker data, recordings and databases on SSD/NVMe. |
| Video blocks | NVIDIA's archived R35.6 Xavier NX multimedia table lists H.264 encode/decode up to 4K60 and H.265 decode up to 8K30 in the specified formats [S2]. These are codec-engine capabilities, not promises that AI inference, storage, or network can sustain that load simultaneously. |
| Carrier and I/O | DFR1242 carrier-specific CSI, M.2/NVMe, GPIO, CAN and power availability must be checked against the board manual before selecting add-ons. Module-level Xavier specifications do not guarantee every dev carrier exposes every interface. |
| Verification | Benchmark measurements are single runs for several cases; independent rerun phase was blocked (R). Accuracy evidence is limited: ResNet INT8 calibration and 50-image FP16 agreement check; YOLO INT8, OCR, pose, depth, tracking, SLAM and application-level accuracy remain unverified. |

## 4. Upgrade path for Poor-rated workloads

Upgrades replace the Xavier module/platform; developer kit and carrier compatibility must be checked separately. TOPS below are vendor peak numbers with sparse/dense distinction, not directly comparable to the measured app rates in `RESULTS.md`.

| Poor workload on this Xavier | Orin Nano Super | Orin NX 16GB | AGX Orin 32/64GB | Best direction |
|---|---|---|---|---|
| Large LLM / long-context or concurrent agents | 8GB RAM remains a constraint despite 67 sparse / 33 dense INT8 TOPS and 102 GB/s bandwidth. | 16GB RAM, up to 100 sparse / 50 dense TOPS, 10–25W modes; meaningful model and concurrency uplift. | 32/64GB, up to 200/275 sparse TOPS, 204.8 GB/s; best for larger models and multiple pipelines. | NX16 for compact local serving; AGX for larger context/concurrency. |
| Multi-stream high-resolution NVR / DeepStream | Better Ampere inference, but 8GB and no NVENC on Orin Nano makes encoding less attractive. | Better GPU, 16GB and NVENC; solid many-stream edge target. | Highest video/AI headroom, 32/64GB, multiple concurrent pipelines. | NX16 for cost-effective recorder; AGX for dense multi-camera analytics. |
| Heavy segmentation / pose / depth / ReID | Good smaller-model upgrade, but only 8GB and no DLA. | 16GB + Ampere + DLA v2/PVA; strong midrange choice. | Most memory, GPU and I/O headroom. | NX16 usually sufficient for compact models; AGX for many streams/large models. |
| Interactive diffusion / image generation | 8GB and limited memory remain bottlenecks; 67 sparse TOPS is not a desktop GPU. | 16GB improves fit; still modest 25W device, validate models. | 32/64GB and 200/275 sparse TOPS is the sensible Jetson option, though still below desktop GPU generation. | AGX Orin; use discrete GPU/remote inference if generation quality/latency matters. |
| Current Isaac ROS 3.x+ / latest JetPack stack | Can run newer JP6 packages (8GB may constrain SLAM/VLM combinations). | Orin NX is explicitly in current Isaac ROS-era support cohort; more RAM/performance. | Best robotics headroom, 32/64GB and high I/O. | Orin NX or AGX; select AGX for nvblox/large sensors. |
| Clinical fall detection / safety-relevant monitoring | More performance does not provide clinical validation. | Improved compute, still requires validated model and certified system design. | More headroom but no substitute for safety/clinical certification. | Upgrade alone does not fix suitability; use validated commercial safety system. |
| Mining / hash throughput | Dense GPU upgrade improves raw throughput, but specialized ASIC economics dominate many proof-of-work algorithms. | Better than Xavier but still an edge inference SoM. | Faster, high power and cost; still not a mining ASIC. | None recommended for economic mining. |

## 5. Five novel uses that exploit idle DLAs, PVA, and NVENC

1. **Heterogeneous observation conveyor:** NVDEC ingests a camera stream, VIC scales/colorspace-converts, PVA/VPI computes motion/ROI cues, DLA runs a supported compact classifier, and GPU runs the occasional unsupported detector; NVENC emits a short annotated evidence clip. This keeps the GPU available for Qwen/Whisper. *Inference/design proposal:* the pieces are supported, but this exact pipeline has not been measured. VPI documents PVA and VIC roles [S4]; media codecs are documented in R35 [S2].
2. **Dual-DLA diversity monitor:** run two different calibrated low-rate classifiers (e.g., people vs. package or visible vs. thermal) on DLA0/DLA1 while GPU handles language, then have deterministic logic reconcile alerts. Use only graphs with actual DLA coverage; measured dual-DLA throughput fell from YOLO 35.76 to 33.85 q/s and ResNet 95.50 to 42.73 q/s, so schedule rather than assume linear scaling (R).
3. **PVA wake-on-change image gate:** continuously downsample/denoise/compute optical flow on PVA/VIC, and wake the DLA/GPU detector only for changed ROIs; NVENC retains a low-bitrate rolling buffer. This is particularly suitable for battery/heat-aware wildlife and doorway sensing. Validate each VPI backend; PVA may not beat GPU for every algorithm [S4].
4. **Vision-guided sales-call context card:** leave Whisper on CPU when the LLM uses GPU (a tested placement finding), put a people/product detector on DLA, use PVA for camera motion/ROI, and NVENC store only opted-in short clips; a small Qwen prompt receives timestamps and labels rather than raw video. In the 60s mixed run, CPU Whisper + GPU Qwen + DLA YOLO yielded 13.3 tok/s and 40.65 q/s (R). This is a consented AVA/RLR research prototype, not an autonomous sales decision system.
5. **Local dataset curator / self-awareness recorder:** DLA labels frames, PVA extracts stable motion summaries, NVENC writes event-only clips, and a small LLM produces searchable natural-language logs. The combination uses fixed-function blocks while preserving GPU bursts for language; store the index on SSD. All end-to-end rates and quality are unmeasured; fan repair required.

## 6. AVA/RLR and ava-stack recommendations

The briefly inspected ava-stack README files describe AVA as an autonomous sales-agent mobile app with an embedded WhatsApp client, local SQLite persistence, on-device ExecuTorch/llama.rn model tiers, local knowledge-base retrieval, and explicit local-only architecture. The RLF project README describes recursive Mamba experiments, while `ava-api` is a separate thin Go service. This makes the Xavier most useful as an **optional LAN sidecar** for sensor perception, transcription, and event memory; it should not become a dependency for existing mobile chat/reply operation.

### Recommended prototype: event-driven, consent-aware sidecar

- **Camera path:** one CSI/USB/IP camera → DeepStream 6.3/Jetson GStreamer decode → YOLOv8n FP16 on DLA0 with GPU fallback, benchmarked against GPU-only; use 35.6 q/s as the conservative measured DLA planning point, not the 67.9 q/s GPU peak when other tasks overlap.
- **Audio path:** whisper.cpp base.en on CPU while Qwen uses GPU, as explicitly tested for the 60 s mixed workload; use push-to-talk or opt-in microphone windows. Prior standalone whisper tiny/base sample RTF was about .52 GPU, while CPU base was approximately 1.0 RTF in Phase D, so CPU placement preserves GPU but is near real-time.
- **Language path:** Qwen2.5-1.5B Q4 via llama.cpp, bounded `-b512 -ub128`; plan around 11.29–13.3 tok/s when sharing. Use 0.5B where low latency and narrow intent labels matter. LLM only summarizes events or drafts a card; deterministic AVA controls pricing, permissions, final messaging and sends.
- **Sidecar contract:** send AVA only `{timestamp, sensor_id, event_type, confidence, short transcription, local clip reference}` over authenticated LAN HTTP/MQTT; do not duplicate raw WhatsApp history or credentials onto the Jetson. Let the Android client retain its current local store and user-visible approval flow.
- **Retrieval:** index short, opt-in event summaries and curated product FAQs in local SQLite FTS5; pass top few relevant records, no video frames or long transcript by default. Keep pricing and product truth in deterministic application data, not model memory.
- **Storage and cooling:** repair fan; attach SSD/NVMe through an actually supported DFR1242 interface or powered USB 3 storage; put models, Docker root, event clips and logs off the SD/rootfs. Bound retention and log volume.
- **Prototype acceptance checks:** application-level sales intent/JSON evaluation, audio/noise and camera accuracy test set, event-to-notification latency, 24-hour thermal/uptime test after fan repair, corrupted-network/sidecar-offline behavior, and duplicate/unauthorized action tests. These are proposed checks; no new tests were run in this research task.

**Recommendation:** adopt the board for a camera+voice+small-model edge sensing prototype and a JetPack 5/TensorRT teaching or compatibility node. Keep it out of production roles requiring current Isaac ROS releases, high-res multi-camera AI, long-context/multi-user agents, safety/clinical decisions, or frequent writes to SD. Fix the fan first, store data on SSD, and retain the phone as AVA's source of truth.
